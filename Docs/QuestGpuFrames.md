# GPU Quest : frames et passes

La capture du travail GPU repose sur le **profiler GPU natif d'Unreal**, dans le canal `gpu` de la même `.utrace`. Ses scopes sont des intervalles mesurés par timestamps GPU, associés au rendu et résolus par le moteur quand les requêtes deviennent disponibles. Ils ne sont pas générés à partir de compteurs Meta ni de l'heure de réception sur le PC. La timeline native de CyInsights les affiche au-dessus du GameThread, avec les autres pistes de la capture.

## Préparation automatique

Sur un Quest détecté, le module Android, chargé à `PostConfigInit`, prépare les requêtes de timestamps **avant l'initialisation du RHI**. Unreal verrouille cette capacité au démarrage : changer une option seulement au début de la trace peut arriver trop tard.

`Project Settings > Plugins > CyInsights > Quest > Prepare Quest GPU Timing` est activé par défaut. Le changement de ce réglage nécessite de relancer le jeu. UE 5 utilise `r.Android.SupportsTimestampQueries`, UE 4.27 utilise `r.Vulkan.SupportsTimestampQueries`. Une surcharge explicite de ligne de commande/console/code est conservée. La préparation ne s'applique pas aux téléphones Android non reconnus comme Quest. Le RHI et le pilote doivent prendre en charge les timestamps ; le plugin ne fabrique pas de support matériel.

La préparation active une capacité du RHI pour la durée du lancement. Selon la version et les statistiques natives déjà actives, Unreal peut effectuer des requêtes GPU même hors enregistrement ; l’absence de trace n’implique donc pas un coût matériel nul. L’option de préparation permet de désactiver ce chemin au lancement. Les passes détaillées et les observations Meta du plugin restent liées à la capture ; le surcoût doit être mesuré sur le jeu/casque cible.

Les modules Shipping, Test et Server restent exclus. Aucune modification ni recompilation du moteur et aucun logiciel de collecte externe ne sont nécessaires à ce chemin natif.

## Niveau de détail

- **GPU groups each frame (default)** / `bGpuTiming` / `gpu=true`, actif par défaut : groupes GPU instrumentés du moteur à chaque frame de rendu. Le profil demande `r.RDG.Events=2`, pour conserver les groupes imbriqués que `RDG_EVENT_SCOPE_FINAL` masquerait au niveau 1, sans ajouter les noms de toutes les passes individuelles.
- **Extra individual GPU passes (each frame)** / `bGpuPasses` / `capture_options.gpu_passes=true` : ajoute les noms des passes (`r.RDG.Events=3`) pendant toute la capture. Les événements de dessin sont activés pour permettre les breadcrumbs du profiler. Les réglages que le plugin change sont restaurés après l'arrêt s'ils n'ont pas été remplacés par l'utilisateur.
- Les snapshots ReShade Windows restent une option indépendante. Le détail natif n'active aucune copie de texture ou de buffer, aucun flush GPU par passe ni capture répétée `profilegpu`.

La couverture varie : les anciens profilers exposent les scopes GPU compilés/instrumentés ; `r.RDG.Events=3` ne transforme pas leurs marqueurs en timestamps de toutes les passes. Les nouveaux profilers peuvent fournir davantage de scopes et de queues, selon le RHI. Les commandes Vulkan individuelles, pipelines, shaders, ressources et le travail interne du compositor Meta **ne sont pas interceptés** par cette implémentation. Un collecteur Vulkan supplémentaire reste nécessaire pour cette inspection.

## Métriques Meta complémentaires

`QuestMetricsHz` / `quest_hz` / `CyInsights.QuestGpuMetricsHz` vaut maintenant **0 par défaut** : le callback `OnEndFrame` observe les compteurs une fois par frame de jeu, sans plafond à 10 Hz. Les valeurs positives de 1 à 120 conservent un mode de polling optionnel. Un doublon de callback pour une même frame ne crée pas un deuxième échantillon. La cadence est réinitialisée à chaque capture/configuration.

Chaque observation conserve la frame de jeu observée, les cycles CPU, les unités, les valeurs brutes et leur validité. L'API [XR_META_performance_metrics](https://registry.khronos.org/OpenXR/specs/1.1/man/html/xrQueryPerformanceMetricsCounterMETA.html) ne fournit pas l'identité GPU d'exécution ni l'intervalle de mesure original : des observations successives peuvent reprendre la même mesure du runtime. Elles ne remplacent jamais les intervalles GPU natifs. Une valeur indisponible ne devient pas un temps GPU nul.

## Format et connexion PC

Le protocole conserve la version 1 et annonce les extensions `native_gpu_passes` et `quest_per_frame_observations`. Un ancien plugin refuse les nouvelles demandes avant démarrage avec une indication de mise à jour. Les profils throttlés compatibles restent utilisables ; le client omet le nouveau champ de passes lorsque le serveur ne le connaît pas. Un ancien INI qui configure explicitement 10 Hz conserve ce choix ; utiliser 0 pour adopter la collecte par frame.

Le manifeste conserve le profil appliqué et le nombre de frames observées Meta. `unreal.gpu.scopes` décrit une capacité **déduite** de l'état du RHI, jamais une preuve de scopes enregistrés : l'analyseur doit constater les événements mesurés. Des résultats GPU encore en vol à la coupure de la trace peuvent manquer ; aucune frame finale manquante n'est reconstruite ni remplie artificiellement.

## Révision des groupes par défaut — 11 octobre 2026

Les groupes sont demandés dans le profil de base, sans shader individuel, timestamp par draw, snapshot ReShade ni copie de ressource. Sur le renderer mobile d'UE 5.5, les scopes `Basepass`, `ShadowProjection`, `Postprocessing` et autres scopes GPU instrumentés dépendent des fonctionnalités réellement rendues. Le niveau RDG 2 expose davantage de groupes sur les nouveaux profilers ; il ne transforme pas les simples marqueurs d'un ancien profiler en timestamps GPU supplémentaires.

La connexion PC affiche si les timestamps natifs sont pris en charge avant de commencer. Le manifeste conserve le résultat de la préparation Android, la disponibilité des timestamps, les niveaux RDG demandé/appliqué et l'état de l'activation des statistiques GPU. Un override explicite empêchant l'activation apparaît dans le diagnostic. Ces informations sont des prérequis, pas une preuve d'événements enregistrés : l'analyse de la trace doit confirmer les groupes mesurés. Les journaux et un bookmark natif gardent aussi le diagnostic de démarrage.

Les durées des groupes délimitent le travail GPU instrumenté. Leur placement relatif au CPU dépend de la calibration du moteur/pilote, qui peut retomber sur un alignement approximatif des frames. Une barre `Basepass` identifie une phase de rendu ; elle ne prouve pas l'instant exact de la rasterisation matérielle interne. Sur un GPU à tuiles, le travail de géométrie et le travail par tuile peuvent être séparés : voir le [guide Vulkan Khronos](https://github.com/KhronosGroup/Vulkan-Guide/blob/main/chapters/tile_based_rendering_best_practices.adoc).

Validation de cette révision : 17 suites CTest passent ; les modules Android ARM64 Development compilent sous UE 5.5 et 5.8 et les modules Windows sous UE 5.8. Les captures rendues Windows contiennent des groupes mesurés dans le profil de base ; le lecteur a résolu 127 libellés RDG sur la capture avec passes individuelles. Le Quest 3 connecté est reconnu (`Oculus`, `Quest 3`), mais le jeu Beyond n'est pas installé sur cet appareil au moment du contrôle : cette révision n'a pas encore été exécutée dans un APK Quest. Il faut intégrer le plugin dans le jeu Development et ré-empaqueter/relancer le jeu pour appliquer la préparation au lancement. Une ancienne `.utrace` sans événements GPU ne permet pas de récupérer le travail GPU absent.

Les quatre captures finales du test Windows contiennent respectivement 21 523, 42 558, 21 326 et 21 012 intervalles GPU complets, avec `BasePass` et `PostProcessing` vérifiés dans chaque profil. Les deux niveaux RDG demandé/appliqué sont conservés après restauration des réglages (2 pour le défaut, 3 pour les passes individuelles). Rapports : `build/quest-gpu-groups-final-validation.log` et `build/quest-gpu-groups-final/*/gpu-summary.json`. Le lecteur compile sous UE 5.5 et 5.8. Les snapshots de la nouvelle application ferment normalement ; le scan Kaspersky local terminé à 16:40:44 ne signale aucune détection. ## Timestamps de fin de pipeline et diagnostic — 11 octobre 2026

Une capture Quest 3 / Vulkan / UE 5.5.3 Meta réelle a été vérifiée dans le lecteur : 9 807 événements GPU, dont 2 178 `MobileSceneRender`, 1 089 `Basepass`, `ShadowProjection`, `MobileFog` et `Translucency` chacun. Autour de la frame examinée, le scope extérieur dure environ 20 ms, mais les groupes imbriqués ne durent que 0 à 1 µs. Leur présence ne suffit donc pas à attribuer le coût de rendu aux groupes.

Le RHI Vulkan de la version 5.5 inspectée enregistre `r.Vulkan.TimestampQueryStage` comme une variable console indépendante, mais choisit le stage à partir d'une autre valeur statique, jamais mise à jour. Un simple changement de CVar ne corrige pas ce chemin. CyInsights détecte à la compilation le chemin lié à la CVar des versions ultérieures. Pour le chemin historique Android, il adapte le pointeur de fonction exporté `VulkanDynamicAPI::vkCmdWriteTimestamp` : pendant la capture uniquement, les écritures TOP_OF_PIPE deviennent BOTTOM_OF_PIPE. Aucun code ni fichier du moteur n'est modifié. L'installation se sérialise avec l'enregistrement RHI ; elle attend des commandes CPU, jamais la fin du travail GPU. Le wrapper conserve le pool, l'index, les autres stages et le mécanisme natif de résolution différée. Après l'arrêt, les appels sont transmis sans changer leur stage ; à la fermeture, le pointeur précédent est restauré seulement si CyInsights le possède encore.

`GPU completion timestamps` / `quest_gpu_completion=true` est activé dans le profil de base et configurable dans Project Settings ou le formulaire réseau. Il ne s'applique qu'aux appareils Quest Vulkan et respecte les surcharges explicites du moteur. Le manifeste conserve `completion_timestamps_requested`, `vulkan_timestamp_stage`, sa signification et `completion_timestamp_path`. Le nouveau profiler GPU conserve son propre chemin de timestamps : le réglage historique n'y est pas déclaré appliqué. Une demande explicite à un ancien plugin Quest sans cette capacité est refusée avant le démarrage ; le client peut choisir le mode historique explicitement. Le SDK/MCP expose le même booléen.

La fin de pipeline peut modifier l'ordonnancement et le coût de mesure ; elle ne garantit pas la séparation des sous-passes d'un rendu par tuiles. Aucune copie de texture/buffer, attente GPU synchrone ou séparation forcée de render pass n'est ajoutée. Les réglages et l'adaptateur restent limités aux builds de développement supportés.

L'application signale `GPU group costs unresolved` lorsqu'au moins quatre scopes imbriqués du segment chargé sont présents, qu'au moins 80 % ont des différences de timestamps <= 2 µs et qu'un scope extérieur dépasse 1 ms. C'est un diagnostic déduit, jamais une déclaration de durée invalide ou de coût réel nul. Les données brutes sont comptées dans les workers de lecture avant l'agrégation graphique par pixel, sans nouvelle passe de lecture ; les valeurs natives sont conservées. Le tooltip distingue une différence de timestamps d'une estimation de coût GPU. La trace Quest réelle s'ouvre avec 5 887 790 événements et le diagnostic est visible sur sa piste GPU.

Validation : 19 suites CTest passent, dont le transfert/restauration des stages, la compatibilité réseau et le diagnostic avant agrégation ; 6 tests SDK et 10 tests Python de packaging/descripteurs passent. Les modules Android ARM64 Development compilent sous UE 5.5 et 5.8. Le symbole utilisé existe dans le binaire Android installé UE 5.5. Ces builds compilent les modules du plugin, sans reconstruire le moteur ni produire un nouvel APK de jeu. Aucun Quest n'est connecté lors de cette révision : le résultat matériel BOTTOM_OF_PIPE et son surcoût restent à confirmer sur une nouvelle capture après intégration et ré-empaquetage du jeu. Les anciennes traces ne sont pas corrigées rétroactivement.

Références techniques : [timestamps Vulkan Khronos](https://docs.vulkan.org/samples/latest/samples/api/timestamp_queries/README.html), [limites du timing à l'intérieur des render passes par tuiles, RenderDoc](https://github.com/baldurk/renderdoc/issues/2659).


## Passes Vulkan sur GPU par tuiles — 2026-10-11

La nouvelle capture confirme que l’adaptateur de stage est actif (`vulkan_timestamp_stage=1`) et ne suffit pas : les sous-groupes restent très courts. Le collecteur complémentaire mesure désormais les frontières des passes graphiques Vulkan dans le plugin CyInsights. Il ajoute deux queries BOTTOM_OF_PIPE **hors** de chaque render pass et compte ses sous-passes, sans découper les passes, intercepter chaque draw, capturer les ressources ni ajouter de soumission GPU. Le mode de base Quest `quest_gpu_completion=true` l’active ; `false` le désactive. Il dépend des API publiques VulkanRHI disponibles dans le moteur sélectionné. Les cibles Shipping/Test/Server sont exclues.

Les query pools suivent les command buffers et leurs générations. Les soumissions graphiques, fences du moteur, resets et libérations sont suivis ; la disponibilité d’une query seule ne suffit jamais à valider une nouvelle génération. La lecture se fait sans WAIT, après fence complétée ou lors de la réutilisation/libération d’un command buffer que Vulkan garantit non pending. Les buffers déjà alloués avant installation peuvent conserver leurs pools en cache jusqu’au teardown ; les allocations suivantes sont associées à leur command pool et libérées avec lui. Aucun GPU wait au début ou à la fin de capture. Le teardown attend le device uniquement si celui-ci existe encore, afin de libérer les pools en sécurité. Les passes en vol au cutoff sont comptées comme pending, sans durée inventée.

Les événements `CyInsightsVulkan.Pass` sont incorporés dans le même `.utrace`, avec timestamps GPU en microsecondes, ordinal de passe, dimensions de render area, nombre de sous-passes, soumission et moment d’observation distinct. Cette observation n’est ni le début GPU ni l’identité de frame exécutée. Les compteurs valides sont déclarés dans `cyinsights.vulkan.passes` ; la capacité réseau est `quest_vulkan_passes`.

Le lecteur local importe ces événements dans **GPU / Vulkan render passes (approximate alignment)**. Les événements supplémentaires sont spoolés sur disque ; seuls les dictionnaires et ancres d’horloge sont conservés en mémoire. L’alignement utilise un échantillon de device clock si l’extension de calibration est déjà activée, sinon les ancres du profiler natif historique. Un intervalle sans ancre exploitable reste indisponible. Une ancienne relation éloignée de plus d’une seconde est rejetée. Les durées sont mesurées ; l’alignement CPU reste explicitement approximatif. Le compteur GPU est traité selon son nombre réel de bits valides, dont les 48 bits du Quest 3. Le choix du lecteur rejette désormais un cache dont les sources sont périmées, même si une version précompilée est présente.

Validation matérielle : Adreno 740, timestamp period 52,083332 ns, 48 bits, aucune extension de calibration annoncée. Deux passes de test donnent environ **0,26 ms** à leurs frontières, contre **0,00125 ms** entre marqueurs internes. La sonde `Tools/QuestVulkanPassProbe.cpp`, compilée avec le code de production du collecteur et des shims de cycle de vie/transport Unreal seulement, récupère **2 passes, 0 pending, 0 dropped**. Une seconde soumission est bloquée avec un timeline semaphore : les anciennes valeurs disponibles ne sont pas consommées ; après signalement, la génération suivante est résolue une fois. Vulkan et les requêtes utilisent le vrai pilote du casque. Ce test n’exécute pas le jeu Unreal ni le writer `.utrace` du plugin.

Le test natif de lecture utilise le même exporteur de passes que l’adaptateur, puis le véritable importeur binaire et l’index paginé : durée, horloge, identité GPU et arrivée désordonnée sont conservées ; une passe non alignable est exclue. Il reste à re-empaqueter le jeu avec le plugin et valider une nouvelle capture complète, puis mesurer le surcoût en situation réelle.

Limites : une passe Vulkan peut réunir Basepass, éclairage, fog et translucence dans plusieurs sous-passes par tuile. Son coût global est mesurable ; ces sous-passes ne reçoivent pas chacune une durée fictive. Les noms sont des identités de passes Vulkan (ordinal/dimensions/sous-passes), pas des noms de shader ou des associations certaines aux groupes Unreal. Les dispatches et transferts hors render pass, le compositor et le stade matériel exact de rasterisation ne sont pas couverts par ce premier collecteur.

Le bouton **GPU Profiling** de Meta Quest Developer Hub concerne les captures GPU de ses outils, notamment Perfetto. [Les notes officielles MQDH 6.5.2](https://developers.meta.com/vr/downloads/package/oculus-developer-hub-mac/) indiquent qu'il est désactivé par défaut et doit être activé pour ces captures. La sonde CyInsights ci-dessus a obtenu ses timestamps Vulkan sans activer ce bouton ; Metrics HUD et Metrics Recording ne sont pas requis pour ce collecteur. Les compteurs `XR_META_performance_metrics` constituent une autre source : le plugin demande lui-même leur activation dans une session OpenXR disponible. La capture Beyond analysée indique encore « Waiting for the Unreal OpenXR backend to initialize » ; activer le bouton MDH ne remplace pas cette intégration du backend.

## Correctif du chemin RenderPass2 — 2026-10-12

La capture Beyond suivante contient `cyinsights.vulkan.passes` activé, zéro passe résolue et deux pending. Le moteur Meta UE 5.5.3 utilise `vkCmdBeginRenderPass2KHR` **et** `vkCmdEndRenderPass2KHR`. Le premier collecteur interceptait le begin mais pas cet end ; ses marqueurs de fin n'étaient donc jamais écrits sur ce chemin. Les deux dispatchs sont maintenant installés/restaurés ensemble. Le canal `cyinsightsvulkan` fait aussi partie des canaux dont l'état est restauré après capture.

La sonde matérielle couvre désormais une passe classique et une passe RenderPass2 dans la même soumission. Le collecteur de production récupère deux intervalles d'environ 0,26 ms, zéro pending et zéro dropped ; les tests de génération bloquée restent valides. Les modules ARM64 compilent avec le moteur Meta 5.5.3 et UE 5.8.3. Archive actualisée : `build/CyInsights-VulkanPass2-plugin-source-20261012.zip`. La validation d'une nouvelle capture dans le jeu reste nécessaire ; remplacer seulement l'application ne change pas le code du plugin déjà installé dans l'APK.

## Détails matériels Meta supplémentaires

Le preset MQDH **Render Pass Diagnosis** représente une autre source. [Le profiler Meta](https://developers.meta.com/vr/documentation/native/android/ts-ovrgpuprofiler/) expose le binning, le rendu par tuile, les chargements/écritures des surfaces et, selon le runtime, des métriques par draw. Le runtime du Quest connecté annonce 58 métriques avec `ovrgpuprofiler -m -x`. La simple activation du bouton ne copie pas ces événements dans la trace Unreal. Le contexte GPU de l'application doit être créé après l'activation du profiling détaillé : le jeu doit être relancé. Meta annonce environ 10 % de surcoût pour ce mode détaillé ; il doit rester une option distincte du collecteur léger.

Ces données système nécessitent la collecte via les outils/API système autorisés du casque, puis l'import et la correspondance d'horloges dans CyInsights. La voie ADB documentée peut être orchestrée depuis le PC sans interface MQDH, mais exige une connexion ADB autorisée, en plus du protocole IP du plugin. Aucune API publique vérifiée ici ne permet au plugin Unreal ordinaire de remplacer cet accès système. L'intégration Perfetto/render-stage Meta est maintenant décrite dans [MetaQuestGpu.md](MetaQuestGpu.md), avec les résultats du petit projet Quest et ses limites ; le collecteur de frontières Vulkan reste une source distincte. Aucun timestamp de réception ou ordinal de surface ne doit être présenté comme une identité certaine de frame ou de groupe Unreal.
